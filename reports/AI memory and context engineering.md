# Copy the cloud's memory tricks, run them locally

As of October 2026, the memory mechanisms behind the leading AI assistants are documented well enough to rebuild on a user's own hardware, and Relic should copy them deliberately. ChatGPT injects a few compact context blocks into every chat: a synthesized profile, recent-chat content and saved facts. Since June 2026 its background "Dreaming" job rewrites that profile after conversations end. OpenAI's new always-on "dots" pair an agent's own browser and app connectors with read-only background research and allow/block/ask rules for actions. Meta's Muse keeps memory as an editable file plus supporting files. Claude offers a client-side, file-based `/memories` tool alongside compaction and context editing. Gemini splits memory into separately switchable layers. Apple's Siri searches an on-device semantic index with a roughly 3B model that fills typed slots. Research agrees on the same shape. Context is a scarce "attention budget" that degrades as it fills, so systems retrieve just in time, compact, consolidate offline, and store memory as episodes, time-stamped facts and procedures. Every one of these mechanisms can run locally. A 16 GB laptop handles capture, indexing, search and answers with 3–8B models, while consolidation (Relic's "dreaming") runs overnight or on a home box. This report specifies a five-tier local memory (raw capture, episodic events, bi-temporal facts, an editable profile and user-approved procedures), exposed to any assistant through a scoped MCP server whose writes go to a review queue and which is hardened against memory poisoning. It also specifies a backfill agent that requests official exports first, fills only the gaps in a visible, pausable browser window at a modest pace while the user handles every login, and hands over to ongoing logging. The one place Relic should diverge from the cloud is deletion: because it holds the sources, the memory and the links between them, forgetting can cascade and be verified. The app should be **unobtrusive, not invisible**: no windows or interruptions, but always a status icon and a one-click pause, because hidden capture is the defining trait of stalkerware.

A note on sources. Much of the product detail below, especially about OpenAI dots and Meta Muse, comes from search-result summaries and secondary blogs, because the researchers could not load the primary pages. Those claims are flagged in the text. Vendor benchmark numbers are self-reported unless stated otherwise.

## Six products, six mechanisms Relic can run on its own hardware

Each major assistant has solved one part of the personal-memory problem well. The useful question for Relic is not whether these products are private enough. It is how each mechanism works, and whether it can run on a laptop and a home server instead of a data center. The answer is mostly yes. The sections below follow the same pattern for each product: how it does it, what Relic copies, and how to do it on-device.

### ChatGPT: context blocks plus overnight "dreaming"

**How OpenAI does it.** A 2025 reverse-engineering analysis, now dated, found ChatGPT appending **four blocks** to the system prompt. Block 1 held interaction metadata (device, usage patterns). Block 2 held recent conversation content: about 40 recent chats, user messages only. Block 3 held the explicit saved memories. Block 4 held dense "user knowledge" summaries regenerated periodically from history. The analysis argued this is a "bitter lesson" design: no retrieval over old chats, just compressed summaries in a large context ([Shlok Khemani](https://www.shloked.com/writing/chatgpt-memory-bitter-lesson)). On **June 4, 2026** OpenAI rebuilt the synthesis step as **Dreaming**, which "automatically curate[s] memories in the background by referencing chat history" after conversations end ([OpenAI](https://openai.com/index/chatgpt-memory-dreaming/); [PCWorld](https://www.pcworld.com/article/3158111/chatgpt-new-dreaming-feature-makes-it-way-better-at-remembering-you.html)). The result is a user-visible, editable **memory summary**, and users can say which topics to raise and when ([ChatGPT release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)). Answers now show which chat, saved detail or file a memory came from ([findskill](https://findskill.ai/blog/chatgpt-dreaming-memory-explained/)). **Project-only memory** confines a project to its own chats, and since August 14, 2026 that setting can be changed after creation ([ChatGPT release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)). Two caveats apply. Whether ChatGPT also retrieves per query is disputed ([mem0](https://x.com/mem0ai/article/2071990201531118063); [theseus-research](https://github.com/TeaShaman-cyber/theseus-research/issues/26)), and the reported jump to **82.8% recall** appears only in secondary sources ([tech-insider](https://tech-insider.org/chatgpt-dreaming-v3-memory-update-2026/)). OpenAI's Atlas browser added opt-in **browser memories**, with a per-site toggle in the address bar that stops memories forming from blocked pages ([OpenAI](https://openai.com/index/introducing-chatgpt-atlas/)). Earlier Relic research cited a report that Atlas was discontinued in August 2026 ([BGR](https://bgr.com/2212396/openai-chatgpt-browser-atlas-discontinued/)); this round's notes could not confirm its status.

**What Relic copies.** Relic copies the four-block prompt layout, the offline consolidation step, provenance on every remembered item, scoped "project" memories, and the per-site memory toggle.

**How to do it on-device.** Relic builds the same four blocks locally:

| Block | Contents in Relic |
|---|---|
| 1. Session metadata | Device, app in focus and time of day |
| 2. Recent activity | A rolling digest of the last few days of episodes |
| 3. Pinned facts | Facts the user explicitly saved |
| 4. Profile | The synthesized profile |

Blocks 3 and 4 are serialized deterministically into a stable prefix so a local runtime's prompt cache can reuse them. A **nightly "dreaming" job** on a 3–8B local model rewrites the profile from the day's episodes and shows the change as a diff. Every line of the profile links back to the events it came from. "Spaces" (work, family, a particular project) play the role of project-only memory. The browser extension gets the same per-site "don't remember this site" switch.

### OpenAI dots: an always-on agent with its own browser and rules

**How OpenAI does it.** Dots, announced on **September 29, 2026**, are always-on ChatGPT agents. Each one has its own cloud computer and browser, connects to apps through OpenAI's plugin ecosystem, and keeps working between chats ([OpenAI](https://openai.com/index/introducing-dots/); [MarkTechPost](https://www.marktechpost.com/2026/09/29/openai-launches-dots-always-on-gpt-6-astra-agents-that-work-from-their-own-cloud-computers/)). Secondary sources describe five mechanics:

- **Memory seeding.** A dot starts with the user's ChatGPT memories, then builds its own from conversations and connected apps.
- **Proactive research.** Background "proactive research" runs only with **read-only tools**, which cannot send messages, edit connected apps, or control a browser or desktop.
- **Custom Rules.** The user can allow, block or require approval for specific actions.
- **Sensitive steps.** Steps such as password changes stay with the user.
- **Local access.** Access to the user's own computer is off by default.

([Vellum](https://www.vellum.ai/blog/official-openai-dots-breakdown); [NeuralTrust](https://neuraltrust.ai/blog/chatgpt-agent-security); [kingy.ai](https://kingy.ai/blog/openai-dots-guide/))

**Flag:** almost every dots detail, including the model name "GPT-6 Astra", comes from search summaries and secondary blogs. The researchers could not read OpenAI's own pages. One blog's claim about a scrapped "GPT-6.1 Astra" could not be corroborated at all.

**What Relic copies.** Relic copies three things: the split between read-only background work and gated actions, the allow/block/ask rule table, and memory seeded from the user's main profile. It also fixes the reported gap that per-dot memory cannot be viewed or edited.

**How to do it on-device.** Relic's background researcher is a local agent that runs while the machine is idle. Its tools are read-only: search over the local memory plus fetching allowlisted public pages. It drafts briefings and suggestions into an inbox and never acts on its own. Anything that changes the outside world, such as requesting an export, needs a matching rule and, by default, the user's approval. The agent's browser is Relic's own isolated profile, not a cloud machine. Its working memory is an ordinary memory space that the user can read and edit.

### Meta Muse: an editable memory file plus supporting files

**How Meta does it.** Meta's **Muse** agent launched in September 2026 ([Meta Newsroom](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)). The Muse Wonder models (October 12, 2026) added **"Active Memory"**, which keeps context across days, weeks and months, and Meta claims state-of-the-art memory scores that nobody has replicated ([Axios](https://www.axios.com/2026/10/12/meta-new-ai-models-anthropic-openai)). Muse stores memory as a user-editable **Memory file** plus **supporting files**. "Forget" searches both and removes matches "as well as it can" ([Meta Help](https://www.meta.com/help/artificial-intelligence/2225571704857152/)). Much of the surrounding detail comes from secondary sources. Manus, now part of Meta, describes the same idea as using "the file system as context" ([Manus](https://manus.im/en/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)).

**What Relic copies.** Relic copies plain, human-readable memory files as the canonical profile, with topic files alongside, and forget implemented as search-and-remove across them.

**How to do it on-device.** The profile and procedural tiers are Markdown files in the encrypted vault, which the user can open and edit like a note. Supporting files hold the detail by topic (people, projects, places). Relic then goes one step further than Muse: forget also follows lineage links into the event store, so both the derived memory and its sources are removed. That closes the gap TIME reported, where forgetting a memory left the original message in place ([TIME](https://time.com/article/2026/10/06/meta-muse-ai-agent-privacy/)).

### Claude: a client-side memory tool, compaction and context editing

**How Anthropic does it.** The consumer app pairs a synthesized, editable memory summary with **tool-based search of past chats**: the model decides when to search, instead of having history injected on every turn. Memory reached the free plan on March 2, 2026, along with an experimental tool for importing memories from other assistants ([MacRumors](https://www.macrumors.com/2026/03/02/anthropic-memory-import-tool/)). For developers, the **memory tool** is file-based and runs on the client. The model issues `view`, `create`, `str_replace`, `insert`, `delete` and `rename` operations on a `/memories` path, and the application maps that path to whatever storage it chooses. When the tool is on, the API adds an instruction telling the model to view its memory directory first and to "assume interruption" ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). Two other mechanisms complement it. **Context editing** clears old tool results on the client side, and **compaction** summarizes the conversation near the window limit, while memory holds "information that must survive summarization" (same source).

**What Relic copies.** Relic copies all three mechanisms: the file-operation memory interface, tool-triggered retrieval rather than always-on injection of everything, and the compaction-plus-clearing loop for long sessions.

**How to do it on-device.** Relic implements a `/memories` backend over its own vault, so Claude, or any model using the same interface, reads and writes memory files that live on the user's disk. It enforces the safeguards Anthropic's documentation leaves to the developer: canonical-path checks against `../` traversal, size caps, expiry of files nobody reads, and stripping of sensitive data. The local assistant runs the same loop. It searches by tool, clears raw tool output once distilled, and compacts while keeping event IDs.

### Gemini: layers with separate switches

**How Google does it.** Gemini keeps three memory layers, each with its own control:

| Layer | What it holds | Default |
|---|---|---|
| Saved info | Facts the user asks Gemini to keep | — |
| Your past chats | Automatic memory of earlier conversations | On |
| Personal Intelligence | Retrieval across Gmail, Photos, Search and YouTube history | Connected apps off |

Google says it does not train directly on the Gmail inbox or Photos library ([Search Engine Land](https://searchengineland.com/personal-intelligence-with-gemini-connect-your-searches-email-photos-and-youtube-history-467521); [datastudios](https://www.datastudios.org/post/does-gemini-remember-past-conversations-context-retention-and-session-behavior)). Gemini's real strength is live retrieval over data that already exists, rather than accumulating new memory.

**What Relic copies.** Relic copies the layered, independently switchable memory and the habit of retrieving from the source instead of copying it into a profile.

**How to do it on-device.** Relic exposes the same three switches: pinned facts, learned memory (episodes, facts and profile) and connected sources (each import and capture source, with "use for answers" on or off). Questions about email or photos go straight to the local index of those sources and are answered there, without promoting the content into long-term facts.

### Apple: an on-device semantic index plus a small model

**How Apple does it.** **Siri AI** was announced in June 2026 and shipped as an English beta with iOS 27 around September 14 ([Apple Newsroom](https://www.apple.com/newsroom/2026/06/apple-introduces-siri-ai-a-profoundly-more-capable-and-personal-assistant/)). It draws on an **on-device Spotlight semantic index** that apps feed through App Schemas and App Intents ([WWDC26 session 240](https://developer.apple.com/videos/play/wwdc2026/240/)), with a per-app "Learn from this App" switch ([Elephas](https://elephas.app/resources/what-is-apple-intelligence)). Heavier queries go to **Private Cloud Compute** ([Futurum](https://futurumgroup.com/insights/will-apples-new-siri-ai-deliver-on-the-promise-of-apple-intelligence/)). The on-device Foundation Model has about 3 billion parameters and offers **guided generation**, which constrains output to a typed Swift schema ([Apple tech report](https://arxiv.org/pdf/2507.13575)).

**What Relic copies.** Relic copies the whole pattern, and Apple is the closest to it architecturally: index locally, extract with a small model into typed slots, and escalate heavy work to a trusted larger machine.

**How to do it on-device.** Relic keeps one local semantic index across all its sources, with a per-app "learn from this app" switch. It uses schema-constrained small models for extraction; on a Mac, that can be Apple's own on-device model. In place of Private Cloud Compute, Relic escalates to the user's **own home box or NAS** for nightly consolidation. Apple's model is not designed as a general chatbot, and its reported 4,096-token window is unverified, so it suits per-event extraction, not reflection.

### What this adds up to, and the one place Relic must diverge

Assembled, the six mechanisms give Relic its whole memory stack:

- **From ChatGPT:** the block-structured prompt and the overnight consolidation job.
- **From dots:** a read-only background agent with an action rule table.
- **From Muse:** editable memory files.
- **From Claude:** a file interface and the compaction loop.
- **From Gemini:** layered switches.
- **From Apple:** an on-device index with a small extractor.

The deliberate divergence is in privacy and deletion, and it needs only a few lines. In the cloud products, **derived memory and its sources have independent lifecycles**. Meta says Muse "may still remember" deleted information. TIME found that "forget" leaves the source message in place. Dots reportedly keep what they learned after an app is disconnected, and per-dot memory cannot be viewed ([Vellum](https://www.vellum.ai/blog/official-openai-dots-breakdown)). Because Relic holds the raw data, the derived memory and the links between them, it can make deletion cascade and then prove it. Memory products also disappear: New Computer's Dot closed in October 2025 ([TechCrunch](https://techcrunch.com/2025/09/05/personalized-ai-companion-app-dot-is-shutting-down)), and Meta acquired Limitless, Rewind's parent company, then switched off Rewind's capture ([luci.memories.ai](https://luci.memories.ai/blog/rewind-ai-shut-down-on-device-replacement)). Finally, memory is now an attack surface. Microsoft documented "AI Recommendation Poisoning", in which attackers plant persistent preferences in an assistant's memory ([Microsoft Security](https://www.microsoft.com/en-us/security/blog/2026/02/10/ai-recommendation-poisoning/)). That risk applies to any system that writes memory automatically, Relic included.

## Research converges on small context windows and time-stamped layered memory

### Context engineering treats the window as a cache, not a warehouse

Anthropic's September 2025 essay defines context engineering as "the set of strategies for curating and maintaining the optimal set of tokens" during inference. It warns of **context rot**: as the window fills, recall from it declines in every model, to varying degrees ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Chroma's report tested 18 frontier models and found degradation in all of them, starting well before the advertised limit. That result is reported second-hand, and the per-model numbers are unverified ([Towards AI](https://pub.towardsai.net/context-rot-is-real-and-its-quietly-breaking-every-ai-agent-you-ve-built-8b11045dff9e)). LongMemEval found that commercial assistants and long-context models lose **about 30% accuracy** when they must remember information across sustained interactions ([LongMemEval](https://arxiv.org/abs/2410.10813v2)).

The practical toolkit has settled into five moves. **Just-in-time retrieval** keeps lightweight references such as paths, queries and links in context and loads the data through tools only when needed. **Compaction** summarizes history near the window limit; Claude Code keeps decisions and open bugs, drops redundant tool output, and resumes with the summary plus the five most recently used files. **Tool-result clearing**, "the lightest form of compaction", removes stale raw tool output. **Structured notes** kept outside the window survive resets. **Sub-agents** explore in clean windows and return summaries of roughly 1,000–2,000 tokens ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Anthropic recommends combining context editing and compaction for long-running agents, with a memory store holding "information that must survive summarization" ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)).

Manus, now part of Meta, adds the cost view. **KV-cache hit rate is "the single most important metric"** for a production agent, because cached input on Claude Sonnet cost $0.30 per million tokens against $3 uncached. The rules that follow are to keep the prompt prefix stable (a timestamp at the top of the system prompt breaks the cache), keep context append-only, serialize deterministically, and mask tools rather than add or remove them mid-run ([Manus](https://manus.im/en/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). Other Manus lessons, such as "reciting" goals in a todo file and keeping errors in context, come from the researchers' background knowledge and were not confirmed this session.

For Relic the conclusion is simple arithmetic. Years of screen text and messages will run to something like 10^8–10^9 tokens, an estimate from the notes rather than a measurement. That is orders of magnitude beyond any context window, and context rot argues against stuffing even what fits. Long context is best used as the **reader** over tens of thousands of retrieved tokens, not as the store. Retrieval plus a curated memory layer is not optional.

### Long-term memory splits into episodes, facts and procedures

The field uses a taxonomy borrowed from cognitive science. **Working memory** is the context window plus a few pinned "core" blocks. **Episodic memory** holds time-stamped events. **Semantic memory** holds facts and profiles. **Procedural memory** holds skills, rules and preferred workflows ([LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)). The founding papers still define the mechanics. Generative Agents scored retrieval as recency (exponential decay) plus LLM-rated importance plus embedding relevance, and ran **reflection** whenever accumulated importance crossed a threshold ([Park et al.](https://arxiv.org/abs/2304.03442)). MemGPT, now Letta, treated the window like an operating system's main memory, paging data in and out of recall and archival stores through function calls ([Packer et al.](https://arxiv.org/abs/2310.08560)). Letta's **sleep-time compute** runs a background agent that rewrites the main agent's memory blocks while it is idle ([Letta docs](https://docs.letta.com/guides/agents/architectures/sleeptime/index.md)). ChatGPT's Dreaming is the consumer version of the same idea.

Updating is where systems differ most. **Mem0** asks an LLM to compare each new candidate fact with similar stored ones and choose ADD, UPDATE, DELETE or NOOP ([Mem0 paper](https://arxiv.org/abs/2504.19413v1)). **Zep's Graphiti** never overwrites. When a new fact contradicts an old one, it marks the old relationship invalid with a timestamp, under a **bi-temporal** model that separates when something was true from when the system learned it ([Zep paper](https://arxiv.org/html/2501.13956v1); [explainer](https://signals.aktagon.com/articles/2026/07/zep-a-temporal-knowledge-graph-architecture-for-agent-memory/)). For personal history, invalidation is clearly right. "Where did I live in 2022?" needs the old address, so deletion should be reserved for what the user actually wants gone. Forgetting has no consensus algorithm. Anthropic suggests expiring memory files that have not been read in a long time ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)), and Generative Agents only decays retrieval scores. The researchers found no rigorous 2025–26 evaluation of forgetting policies.

The open-source frameworks are almost all permissively licensed, which matters for a local product. Mem0 (including OpenMemory), Graphiti, Letta, Cognee, MemOS and Memobase are Apache-2.0. LangMem, A-MEM, GraphRAG, HippoRAG, LightRAG and ColPali are MIT, each checked against its repository's LICENSE file in October 2026 ([mem0](https://github.com/mem0ai/mem0); [graphiti](https://github.com/getzep/graphiti); [letta](https://github.com/letta-ai/letta); [LightRAG](https://github.com/HKUDS/LightRAG)). Zep's own server Community Edition was reportedly deprecated, so Graphiti is the open path ([Atlan](https://atlan.com/know/zep-vs-mem0/), single secondary source). **OpenMemory MCP** is the reference local design. It is a local server with `add_memories`, `search_memory`, `list_memories` and `delete_all_memories`, so several assistants can share one store with no cloud ([Mem0 docs](https://docs.mem0.ai/openmemory)). Indexing cost shapes the choice. **LazyGraphRAG** defers summarization to query time and indexes at 0.1% of full GraphRAG's cost ([Microsoft Research](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)). That matters when thousands of screenshots arrive every day.

### Benchmark numbers are mostly marketing, so build a private eval

The serious public benchmarks are **LongMemEval** (500 questions testing extraction, multi-session reasoning, temporal reasoning, knowledge updates and abstention) ([arXiv](https://arxiv.org/abs/2410.10813v2)), **MemoryAgentBench** (ICLR 2026, 2,071 questions over 103k to 1.44M tokens) ([arXiv](https://arxiv.org/abs/2507.05257)), and **BEAM**, which runs at 1M and 10M tokens across ten categories including contradiction resolution and event ordering ([Mem0](https://mem0.ai/blog/state-of-ai-agent-memory-2026)). Mem0 self-reports **64.1% at BEAM-1M falling to 48.6% at BEAM-10M** and calls that drop the field's key open problem ([Mem0](https://mem0.ai/blog/state-of-ai-agent-memory-2026)). The older LoCoMo benchmark is saturated and contested. Zep said Mem0's paper misconfigured Zep and reported 75.14% instead of 65.99% ([Zep](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)). In Mem0's own original table, a plain full-context baseline scored about 73% against Mem0's best of about 68% ([memoryplugin](https://www.memoryplugin.com/wiki/evaluating.html)). One system's "100%" retrieved 50 items per query, which is effectively the whole conversation ([Vectorize](https://vectorize.io/articles/mempalace-benchmarks)). What memory layers reliably buy is speed and cost: Mem0 reported p95 latency of 1.44 s against 17.1 s for full context ([Mem0 paper](https://arxiv.org/abs/2504.19413v1)). The lesson is that **at short scale long context wins, and memory systems pay off at scales beyond the window**, which is where a lifelog lives.

No public benchmark resembles a lifelog: multimodal, multi-source, years long, full of aliases. Relic should build its own eval of a few hundred questions over a consenting tester's data, stratified by the LongMemEval and BEAM categories, with the model and judge held fixed across runs. It should also add something no public benchmark tests: **post-deletion leakage**. After a user forgets an item, can any query, summary or profile still surface it? That is exactly what Muse appears to fail, and it is the test that turns Relic's privacy claim into a number.

## A 16 GB laptop runs the daytime path; consolidation waits for night

Every mechanism above runs locally. The constraint is not whether it can, but when. Real-time work has to be cheap enough to run beside the user's own apps. Anything that reads a whole day of activity belongs in an overnight batch, which is exactly how ChatGPT's Dreaming and Letta's sleep-time agents already work in the cloud.

### What the evidence says about local speed

Measured figures in the notes are sparse, and most are vendor or blog numbers.

**Capture.** The capture engine itself is light. Screenpipe-style capture is reported at **about 5–15% CPU and 0.6–3 GB of RAM** ([Mintlify guide](https://www.mintlify.com/screenpipe/screenpipe/advanced/performance)). Reading the accessibility tree first keeps OCR rare.

**Speech recognition.** On an M4 Pro, Parakeet TDT 0.6B transcribed a 5-minute clip in **2.91 seconds against 20.92 for Whisper large-v3-turbo** ([Parakeety](https://www.parakeety.com/resources/parakeet-v3-vs-whisper-large-v3-turbo)). Parakeet covers about 25 European languages, so Korean audio needs Whisper.

**Visual retrieval.** The 250M-parameter **ColModernVBERT** encodes a query on CPU in **0.032 seconds against 0.222 for ColPali**, at nearly the same retrieval quality (ViDoRe 68.6 vs 69.2) ([emergentmind](https://www.emergentmind.com/topics/colpali)). Visual search therefore works on CPU at query time. Indexing many screenshots is heavier, so it should be batched.

**Memory-layer latency.** Mem0's search took **0.148 seconds at the median**, against about 10 seconds for stuffing a full conversation into context ([Mem0 paper](https://arxiv.org/abs/2504.19413v1)).

**Agents.** Open-weights agents trail frontier ones. Earlier Relic research found ByteDance's UI-TARS-2 at **47.5%** on the OSWorld desktop benchmark, while aggregators put frontier agents at about 85% ([Codesota](https://codesota.com/model/ui-tars-2); [a16z](https://a16z.com/can-agents-use-a-computer-yet-weve-got-the-data/)). The 4B **Holo3.1-4B** reportedly reaches 71% on AndroidWorld, per aggregator data ([BenchLM](https://benchlm.ai/benchmarks/androidworld)). Cloud agents that call a model on every step take 2–5 seconds per step ([devtoollab](https://devtoollab.com/blog/best-ai-browser-automation-tools)).

**Gaps.** The notes contain **no measured tokens-per-second figures for local 3–8B models on consumer Macs or PCs**, and no throughput data for UI-TARS or Qwen-VL on-device.

### A job-by-job hardware plan

The table assigns each memory job to a model class and a time slot. Model sizes follow the research above. **The RAM column is a back-of-envelope estimate, not a measurement.** It assumes 4-bit quantized weights at roughly 0.5–0.6 bytes per parameter, plus working memory, and should be replaced with Relic's own benchmarks in the first engineering spike.

| Job | Model class | When it runs | Rough RAM (estimate) | Notes |
|---|---|---|---|---|
| Screen text | OS accessibility API, then native OCR | Real time | Small | Accessibility text first; OCR only for canvases and images |
| Text embedding of new events | Sub-1B multilingual embedder | Near real time, in small batches | Under 1 GB | Cheap enough to keep the index fresh |
| Visual index | ColModernVBERT-class (~250M), with pooling | Overnight for indexing; real time for queries | About 1 GB | Pooling cuts vectors 16–516× ([arXiv 2609.07262](https://arxiv.org/pdf/2609.07262)) |
| Speech recognition (opt-in) | Parakeet 0.6B; Whisper turbo for Korean | Near real time, gated by voice detection | 1–3 GB | Own microphone only |
| Per-event extraction | ~3B with schema-constrained output (Apple's on-device model on a Mac, or a 3–4B open model) | Mostly overnight; real time only for high-salience events | 2–3 GB | Small window; one event at a time |
| Answering questions | 3–8B instruct model with the cached profile prefix | Real time, on demand | 3–6 GB | Retrieval keeps prompts short |
| Nightly "dreaming" (digests, fact updates, entity merges, contradiction checks) | 7–8B locally, or larger on a home box with a GPU | Overnight, plugged in and idle | 5–6 GB on a laptop | The job that most needs a bigger model |
| Weekly profile and procedure proposals | Same as the nightly job | Weekly, overnight | Same | Output is shown to the user as a diff |
| Deletion cascade and leakage test | Indexes plus the same models | On demand; re-derivation overnight | Same | The deletion runs immediately; re-summarizing can wait |
| Agent exception repair | Local vision-language model (UI-TARS / Qwen-VL class, 4–8B) | Only when a recipe step breaks | 4–6 GB | Most agent steps are deterministic code with no model at all |

Three practical conclusions follow. First, an **8 GB machine** can capture, index and search, and can answer with a 3–4B model, but it should hand nightly reflection to a home box or skip deep consolidation. Second, a **16 GB Apple Silicon or comparable PC** can run the whole stack, as long as reflection runs one job at a time while the user is away. Third, **a NAS or mini-PC with a GPU** becomes Relic's equivalent of Apple's Private Cloud Compute. It is the place for 8B-plus models, re-embedding after model upgrades, and building the visual index, and the user owns it. A frontier cloud model remains an opt-in for hard questions and new agent flows, and receives only redacted inputs.

What must be batched is everything that reads across events: fact extraction beyond the salience gate, entity resolution, day and week digests, profile regeneration, visual index building, re-embedding, and re-derivation after deletions. What must stay real-time is small: capture, text extraction, inserting into the full-text index, embedding new text, and answering a question against what is already indexed. That split also gives the user a calm machine during the day, which matters for the "unobtrusive" principle discussed later.

## Relic's memory layer: five tiers, one immutable source, deletion that cascades

### The tiers and what each one is for

The design below is an inference from the research above, adapted to a desktop product that already captures screen text and imports exports. Its organizing rule is that **raw data is the source of truth and every derived item points back to it**. That makes compaction restorable, in Manus's sense, and makes forgetting verifiable.

| Tier | Contents | Built by | Storage and index | Lifecycle |
|---|---|---|---|---|
| **0. Raw capture** | Screen frames, accessibility and OCR text, browser events, export files, imported messages | Capture engine and importers | Immutable, content-addressed encrypted blobs; tiered retention (full frames, then keyframes, then text only) | Kept until the user deletes them or a retention tier expires them |
| **1. Episodic events** | Normalized events: "read page X in app Y from 14:02 to 14:09", "saved Instagram post Z", "messaged Minji" | Deterministic parsers plus a small local model for segmentation and titles | SQLite with FTS5 (trigram tokenizer, for OCR noise and Korean), a vector index, and an optional visual index | Append-only; each event lists its raw source IDs |
| **2. Semantic facts and entities** | People, places, projects, preferences and relationships, each with `valid_from`/`valid_to` (event time) and `recorded_at`/`invalidated_at` (ingestion time) | Nightly extraction with ADD/UPDATE/INVALIDATE/NOOP decisions, Graphiti-style | Bi-temporal entity graph in SQLite or embedded Graphiti; reversible `same_as` merges | Invalidated, not overwritten; deleted only by the user or a cascade |
| **3. Profile (core blocks)** | A few hundred to a few thousand tokens: who the user is, current projects, standing preferences | Weekly reflection, shown to the user as a diff | Plain text files, Letta- or memory-tool-style | Regenerated from tier 2; never edited by third-party content |
| **4. Procedural** | How the user wants assistants to behave; approved workflows and agent recipes | **Only the user**, or a proposal the user approves | Versioned files | Changes only with user sign-off |

Every item in tiers 1–4 carries a **provenance record**: the source event IDs, the author (the user, another named person, or an unknown web page), a trust level, sensitivity tags (health, finance, intimate, other people's data), a confidence score and a last-accessed time. Trust follows authorship, not the platform. A post the user wrote is user-authored. An Instagram post the user saved is **two** things: the act of saving is a user-authored signal ("interested in ceramics"), while the caption is untrusted third-party text that may never become an instruction.

**Entity resolution** across sources is where lifelogs get hard, and the researchers found no primary source on cross-platform identity matching. The sensible order is deterministic keys first (email, phone and platform IDs from exports), then name and embedding similarity, with an LLM proposing merges that the user confirms. Merges are stored as reversible `same_as` edges so a wrong merge can be undone.

### Small models fill typed slots; storage is the visual index's real cost

The hardware plan above assigns the models. Two design details matter for the memory layer itself. First, extraction should always use **schema-constrained output**, the way Apple's guided generation does. A small model that can only fill typed fields such as person, place, time or claim is easier to check, and it gives injected text far less room to do harm. Apple's reported 4,096-token on-device window comes from a third-party guide and is unverified against Apple's documentation ([blakecrosley](https://blakecrosley.com/es/blog/apple-foundation-models-framework)). Second, late-interaction visual models such as ColPali store about 1,031 vectors per page, so **storage, not compute, is the visual index's cost**. MUVERA encodings let ordinary vector search reach 99.4% of brute-force quality ([Mixpeek](https://blog.mixpeek.com/colqwen2-muvera-multimodal-late-interaction/)). Combined with pooling, a compressed visual index used as a reranker behind text search fits on a laptop.

### Reflection runs while the user sleeps

Relic's version of Dreaming and sleep-time compute is a set of jobs that run when the machine is plugged in and idle. **Nightly**, the jobs segment the day into episodes, write a day digest with citations to event IDs, extract candidate facts and run the update decision against existing facts, propose entity merges, and flag contradictions ("two different job titles this month"). **Weekly**, the profile blocks are regenerated from the current valid facts and shown to the user as a diff to accept or edit, which is the transparency ChatGPT added in June 2026 and dots reportedly lack. Procedural proposals ("you always ask for answers in Korean, then English") are queued for approval. **Monthly**, a decay pass lowers the retrieval priority of facts that are never accessed, offers to archive stale ones, and re-checks sensitivity tags. Following Generative Agents, salience should gate how much expensive extraction each event gets, with full LLM extraction only for events that score high, LazyGraphRAG-style.

### Context assembly follows the cache

When the user, or an assistant over MCP, asks a question, Relic assembles context in a fixed order. First comes a **stable prefix**: system instructions plus the profile blocks, serialized deterministically so the KV cache is reused across turns, as Manus advises. Then come **just-in-time results** from hybrid search (FTS plus vectors plus graph neighbors, filtered by time). Broad questions such as "what did I work on in March?" go to **sub-agents** that each search one source or one time range and return short summaries with event IDs. Raw tool output is cleared once it has been distilled. Compaction always keeps the event IDs, so any summary can be expanded back to its sources. Timestamps go in the retrieved results, never in the prefix.

### Forgetting is a cascade, and Relic should prove it

This is where Relic can beat every cloud product in the table. When the user deletes a raw item, a source, a person or a topic, Relic walks the lineage graph. It deletes the raw blobs and their index entries, tombstones the events that cite them, re-derives or deletes every fact whose only support was those events, and regenerates any digest or profile block that cited them. It then runs the post-deletion leakage test from the private eval against the deleted content and shows the user the result: "Forgot 214 items, 9 facts and 2 digest paragraphs. No query now returns them." Revoking a source works the same way, with a choice the user makes explicitly: stop future capture only, or also purge what was learned. That is the choice dots reportedly do not offer. Vector indexes need real deletion, not just filtering, and encrypted offsite snapshots need a re-key or expiry schedule so deleted data does not live on in backups. Relic should be honest about the limit: **anything already sent to a cloud assistant is outside its reach**. That makes the egress ledger described below essential.

### MCP turns Relic into memory for any AI, behind a narrow door

The Model Context Protocol lets Claude, ChatGPT, Cursor or a local model use Relic as their memory without Relic choosing a vendor. OpenMemory proves that the local pattern works ([Mem0 docs](https://docs.mem0.ai/openmemory)). But Claude's memory-tool documentation is explicit that storage, scoping and security are the application's job. It requires blocking path traversal, capping sizes, expiring files and stripping sensitive data, because the model's own reluctance to store secrets "is not a guarantee" ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)).

| MCP tool | Kind | Behavior |
|---|---|---|
| `search_memory(query, time_range, sources, people)` | Read | Hybrid search; returns snippets with event IDs, timestamps and trust labels; redacted by default |
| `get_event(id)` / `timeline(range)` | Read | Expands a citation; respects the client's source scope |
| `get_profile(scope)` | Read | Returns the profile blocks allowed for this client (for example "work" only) |
| `propose_memory(text, evidence_ids)` | Write, queued | Lands in a **review queue**; the user approves, edits or rejects it in Relic's own interface, never in the chat |
| Deletion | Not exposed | Forgetting happens only in Relic's interface, so a hijacked client cannot erase evidence or trigger a purge |

Scoping is per client and per session. A coding assistant might see browser and editor history but never messages. Health, finance and intimate categories are excluded unless granted one by one. Read tools carry the protocol's read-only annotations, and each new client session needs the user's approval ([MCP spec](https://modelcontextprotocol.io/specification)). Every query and every returned item goes into an **egress ledger**: which client received which items, when. This matters more than it first appears. A result returned to ChatGPT becomes part of a ChatGPT conversation, and Dreaming may then fold it into OpenAI's cloud memory. The ledger is how a user later finds and deletes what left the device. Relic's setup should also suggest turning on project-only memory, or turning off assistant memory, for chats that use Relic. A local assistant should be the default client, and cloud clients should get redacted, summarized results unless the user widens access.

### Poisoning defenses assume the model will be fooled

A lifelog ingests exactly what memory attacks use: web pages, email, other people's messages and screenshots full of text. The documented attacks are specific. **SpAIware** (September 2024) used a web page to plant instructions in ChatGPT's memory so that every later chat leaked data ([The Hacker News](https://thehackernews.com/2024/09/chatgpt-macos-flaw-couldve-enabled-long.html)). In February 2025 Gemini was tricked through **delayed tool invocation**: an injected document conditioned a memory save on the user's next ordinary reply, getting around Google's rule against memory writes while reading untrusted data ([Gigazine](https://gigazine.net/gsc_news/en/20250214-prompt-injection-gemini-long-term-memory/)). Earlier Relic research noted that Brave demonstrated injections in faint text that people cannot see but OCR reads ([Brave](https://brave.com/blog/unseeable-prompt-injections/)), and that Anthropic's best published defense still allows **about 1% attack success against an adaptive attacker** ([Anthropic](https://www.anthropic.com/research/prompt-injection-defenses)).

The design therefore relies on structure, not on the model's judgment. Extraction uses schema-constrained output, so captured text can fill only typed fields. Anything derived from third-party content enters tier 2 as **quarantined** and cannot reach the profile or procedural tiers without user review. Procedural memory, the tier that tells assistants how to behave, accepts writes only from the user. Memory writes are never triggered by conversation, because the Gemini attack showed that "the user just said yes" can be engineered. Approval happens in Relic's own interface, showing the evidence. Retrieved memory is always returned to assistants as quoted data with provenance, never placed in tool descriptions or system text. Every change to tiers 2–4 is logged as a diff, and the store is snapshotted so a poisoning can be rolled back to a known-good date. A small set of canary documents containing planted instructions should run through the pipeline in continuous testing.

## The backfill agent asks for exports first and fills only the gaps in plain sight

### Exports give identifiers; the agent supplies what they omit

A capture-only product starts cold, which was Rewind's problem. Readwise shows the healthier pattern: connect, optionally import all past items once, then sync daily ([Readwise docs](https://docs.readwise.io/readwise/docs/importing-highlights/twitter)). Official exports, however, mostly deliver identifiers and links rather than content, and some leave out whole categories.

| Platform | What the official export gives | Main gap | Gap-fill plan |
|---|---|---|---|
| **Google / YouTube** | Takeout; links expire after 7 days and allow 5 downloads ([takeoutday](https://takeoutday.org/guides/how-to-export-youtube-data)) | Watch history may cover only recent years, unavailable videos drop out, and time-zone abbreviations cause duplicates ([youtube-watched](https://github.com/VldmrB/youtube-watched)) | Parse Takeout; optionally read the History page for recent entries; normalize time zones |
| **Instagram / Facebook** | Accounts Center JSON or HTML; activity files carry post links ([Redact](https://redact.dev/blog/instagram-data-file-download)); earlier research found Meta exports must be downloaded within 4 days ([Meta Help](https://www.meta.com/help/artificial-intelligence/1314808549771571/)) | Whether saved collections and media are included is **unverified**; deleted items are unreliable | Open the Saved page once per collection to record membership, captions and media, as local extensions such as Instagram Exporter do ([Chrome Web Store](https://chromewebstore.google.com/detail/aegonmaomboambpppdbbekomkmehplln)) |
| **X** | Archive | **Bookmarks are not in the archive** (vendor guide) ([ContextBolt](https://contextbolt.com/blog/export-twitter-bookmarks/)) | Prefer the official API, as Readwise does; otherwise walk the Bookmarks page in the user's session |
| **Reddit** | Data request; `saved_posts.csv` has only an ID and a link ([ContextBolt](https://contextbolt.com/blog/export-reddit-saved-posts/)) | No titles or content; the interface shows only about 1,000 saves ([ContextBolt](https://contextbolt.com/blog/reddit-save-limit-workaround/)) | The CSV gives the complete ID list; enrich each one by opening the permalink. Earlier research reports Reddit closing public API access in March 2027 ([TechCrunch](https://techcrunch.com/2026/09/30/reddit-is-killing-rss-feeds-ending-public-api-access-because-of-ai-bots/)), so do this early |
| **TikTok** | TXT or JSON in 24 hours to 4 days, metadata and URLs only ([takeoutday](https://takeoutday.org/guides/how-to-export-tiktok-data)); choose "All data", because custom exports dropped browsing history ([DTI](https://portmap.dtinit.org/articles/watch-history3.md/)) | No captions or media | Enrich favorites only; opening every watched link is costly and low value |
| **Pinterest** | No official export documentation found | Private boards need individual export ([Greasy Fork](https://greasyfork.org/scripts/489596-pinback-next)) | Walk each board |
| **Kakao, Naver** | **No sources found** this session | Unknown | Per-chat KakaoTalk export (from earlier research); revisit when Korea's PIPA transmission right reaches large private firms on 20 February 2027 |

Timelinize's open-source importers are a useful reference for parsing Facebook, Instagram and Takeout archives, and the project's advice to keep the original exports is right ([Timelinize source](https://gitdab.com/cobertos/timelinize/src/branch/main/datasources/instagram/instagram.go)).

### How the agent should run

The backfill runs in five stages. **Stage one is consent and planning.** For each connected platform, Relic shows a card listing what the official export covers, what the agent would add, roughly how long that will take at the default pace, and a plain-language risk note (see below). The user turns each platform on or off individually. **Stage two is requesting every export in parallel.** The agent deep-links the user into each request page, and the user clicks "request" while logged in. Relic then tracks each request ("requested, expected in 1–4 days") and reminds the user before Takeout or Meta links expire. Earlier research found that no platform sends a "your export is ready" webhook, so Relic watches only for the one notification email from the known sender. **Stage three fills gaps that no export covers**, such as X bookmarks and Instagram collections, starting immediately so the product is useful on day one. **Stage four runs when the exports arrive.** Relic parses them locally, works out which IDs lack content and which categories are missing, and queues enrichment jobs. **Stage five hands over to ongoing logging.**

The agent itself should be mostly **deterministic code with a model for exceptions**. Session-bound tools read the structured data a logged-in page already loads, rather than reading pixels. The notes estimate this is 10–100 times cheaper per item than a vision agent, an architectural estimate rather than a measurement. Stagehand's caching shows the cost lever: the first run uses the model, and later runs replay the cached action with no model cost ([Stagehand docs](https://docs.stagehand.dev/v3/best-practices/cost-optimization)). A pure screenshot agent at 2–5 seconds per step would cost roughly $15–30 per thousand items, a rough inference from one unverified per-step price ([devtoollab](https://devtoollab.com/blog/best-ai-browser-automation-tools)). A local vision model steps in only when a layout changes or a "load more" control behaves oddly, and the user approves any repaired step before it is saved to the recipe. No published benchmark measures items per hour for consumer-account backfills, so Relic must measure its own.

**Where the agent runs.** It runs on the user's own machine and home connection, in a **dedicated Relic browser profile** where the user signs in to each platform themselves. It does not run in the user's everyday profile, so the agent never touches other sites' cookies or saved passwords. It never runs in a cloud browser. This follows earlier Relic research and the security record of agentic browsers. The trade-off is that the first sign-in from a new profile may trigger a platform's new-device check, which the user simply completes.

**Pace and caps.** The agent runs at a steady, modest rate with a per-platform daily cap that the user can see and lower. A useful reference is one vendor's free-tier limit of 50 saved posts a day for Instagram ([SaveVault](https://webmail.hunted.space/product/savevault)). The researchers found no published thresholds at which platforms block accounts, so Relic's defaults should be conservative and tuned from opt-in telemetry of failures only, never of content. The point of pacing is to limit load and protect the user's account. It is not camouflage. Relic adds no fake mouse movement, rotates no fingerprints or IP addresses, and changes no user agent. Instaloader's experience supplies one concrete rule: restarting repeatedly after a rate limit makes things worse, because each restart assumes a fresh budget ([Instaloader](https://git.sudo.is/mirrors/Instaloader/src/branch/master/docs/troubleshooting.rst)). So **any rate-limit, "try again later" or suspicious-activity screen stops that platform for the day** and tells the user, with no automatic retry loop.

**Checkpoints.** Each platform and collection keeps a cursor holding the last item ID and timestamp seen. Every write is idempotent, keyed by the platform's canonical item ID, which also handles infinite-scroll lists that unmount earlier items. The backfill walks newest to oldest until it reaches the export's oldest ID or the end of the list, so a reboot resumes where it stopped instead of re-fetching.

**The human in the loop.** Login, two-factor prompts, CAPTCHAs and account checkpoints always pause the run and hand control to the user, in the visible window. The model never receives passwords, codes, cookies or tokens. Claude in Chrome, generally available since August 26, 2026, shows the same pattern of asking for approval at sensitive moments ([Gigazine](https://gigazine.net/gsc_news/en/20260827-claude-chrome-available/)).

**Visibility.** The agent's window shows a persistent banner ("Relic is reading your Instagram Saved: collection 'Recipes', 312 of about 1,200"), with Pause and Stop for each platform and a local log of every page visited. The status icon reflects that an agent is running even when the window is minimized.

**Injection containment.** Page content such as captions and comments flows only into the store, as untrusted data. The agent's possible actions are fixed by the recipe: a domain allowlist, read-only navigation, and no composing, posting, deleting or arbitrary script execution. A malicious caption therefore has nothing to steer.

### Say the terms-of-service risk out loud

The legal picture favors the user's own agent on hacking law but not on contract. In August 2026 the Ninth Circuit reportedly vacated the injunction against Perplexity's Comet agent, with Judge Milan Smith Jr. writing that it is the *user* who "accesses" Amazon's computers with the assistant's help. The case is remanded, and the primary opinion was not read ([Courthouse News](https://courthousenews.com/ninth-circuit-lifts-block-on-ai-powered-shopping-assistant/)). Contract risk remains. Instagram's terms bar collecting information "in an automated way without our express permission" ([Instagram Help](https://help.instagram.com/581066165581870)). The logic of *Meta v. Bright Data*, which turned on being logged off, implies that a logged-in account holder is bound by those terms ([Farella Braun + Martel](https://www.fbm.com/post/102kqw7/)). The realistic consequence for an individual is a temporary block or account checkpoint, not a lawsuit, but the user should hear that before choosing. Relic's consent card should say plainly: this platform's terms may prohibit automated collection, even of your own saved items; the official export carries no such risk; the agent runs slowly and stops at the first warning; you can skip this platform. Disguise is what turns tolerated automation into conflict. Earlier research noted that Amazon's suit alleged Comet posed as ordinary Chrome. If Relic ever runs anything remotely, it should identify itself with **Web Bot Auth**, now an IETF Standards Track draft from Cloudflare and Google authors ([IETF](https://datatracker.ietf.org/doc/html/draft-ietf-webbotauth-httpsig-protocol)), though a local agent in the user's own session has no remote infrastructure to sign with.

### Switching to ongoing logging retires the agent

The backfill ends when each cursor meets the export's oldest ID. From then on, the order of preference is clear. First come official APIs and scheduled exports. Google Takeout can be scheduled every two months (from earlier research), and X bookmarks can sync daily through the API, as Readwise does. Second comes **capture at the moment of action**: Relic's browser extension and screen capture see a save, like or bookmark as the user makes it, so nothing needs re-crawling. Third, for anything still missed, comes a light daily check that reads only the top of a list until it hits an already-seen ID, run visibly under the same caps. Over time the crawling agent's role shrinks toward zero, and so does its terms-of-service exposure. The raw exports are kept locally permanently, as Timelinize advises, because they are the user's only proof of what the platform held.

## Unobtrusive, not invisible

The user asked for Relic to be "not visible while it's on". The right reading of that request is **unobtrusive**: no windows, no pop-ups, no interruptions during normal capture and reflection. It should not mean **invisible**, for three reasons.

First, the operating systems will not allow it, and Relic should not try. Earlier research documented that macOS asks the user to re-approve screen recording roughly monthly ([9to5Mac](https://9to5mac.com/2024/08/14/macos-sequoia-screen-recording-prompt-monthly/)). Android requires fresh consent for each screen-capture session ([Android Developers](https://developer.android.com/media/grow/media-projection)). iOS broadcast capture shows a red indicator ([Apple Dev Forums](https://developer.apple.com/forums/thread/651367)). These indicators exist precisely so that capture cannot be hidden from the person at the keyboard, and a product built to suppress them would be fighting the platform owner.

Second, **hidden capture is the defining trait of stalkerware**. What separates a personal tool from a monitoring tool is who installs it, whether the recorded person knows, and whether the data can reach someone else. The Coalition Against Stalkerware, founded by EFF, antivirus vendors and advocacy groups, maintains shared detection criteria built around exactly those traits ([EFF](https://www.eff.org/press/releases/eff-antivirus-companies-and-human-rights-groups-launch-coalition-combat-stalkerware)). An app with a hide-the-icon option invites antivirus flags and store rejection. Google Play, for example, already bans accessibility services used to plan and execute actions autonomously ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)). Such an app also becomes the tool an abusive partner installs, and it creates legal exposure the moment it captures someone other than the owner. Recording a conversation you are not part of carries 1–10 years in prison in South Korea, and about a dozen US states require every party's consent to record audio ([Segye Ilbo](https://www.segye.com/newsView/20220822516779); [Layer3 Labs](https://www.layer3labs.io/guides/two-party-consent-states)).

Third, visibility is what makes the product trustworthy to its own user. Recall's default-on launch caused a backlash that still shapes how people see it ([Engadget](https://engadget.com/ai/brave-and-adguard-now-block-microsoft-recall-by-default-152601475.html)).

The concrete design is a **persistent, minimal menu-bar or tray icon** whose state shows at a glance: capturing, paused, agent running or reflecting. One click pauses everything. Pause durations are offered ("for an hour", "until tomorrow"), and capture pauses automatically for excluded apps and private windows. There are no notifications during normal operation. The optional daily digest waits until the user opens it. **Setup is owner-only**: it happens on the device, gated by the owner's biometric or passcode, and is re-confirmed periodically. The app cannot be renamed, disguised or hidden from the app list. It has no remote viewer, and uninstalling it takes one discoverable step that wipes the vault. Relic should be quiet in the way a good backup app is quiet, not in the way spyware is.

## Conclusion

The memory race between OpenAI, Meta, Google, Anthropic and Apple has made one thing clear: the technical recipe is no longer secret. A small synthesized profile, just-in-time retrieval, background consolidation and time-aware facts are documented, open-sourced and mostly permissively licensed. On consumer hardware the binding constraint is scheduling, not capability: Relic's "dreaming" simply has to happen while the user sleeps. What none of the cloud products can credibly offer is **lineage the user controls**. Their memory is a derivative the vendor keeps, with a lifecycle independent of its sources, so "forget" degrades into "as well as it can". Relic's differentiator is therefore not better recall. It is a measurable forgetting guarantee: a post-deletion leakage test it runs and shows to the user, which no cloud vendor publishes. Relic should treat that number as a headline product metric.

The second implication is that "memory for any AI" through MCP cuts both ways. It makes Relic the user's portable context, worth more as assistants multiply and as vendors compete on memory import. But every result Relic sends to a cloud assistant can be absorbed into that vendor's memory. The egress ledger, default redaction and a review queue for writes are what keep Relic the source of truth rather than a feeder for someone else's profile of the user. The backfill agent follows the same logic over time: it is a bridge, meant to shrink as official feeds and capture at the moment of action take over, and the less it has to do, the less it puts the user's accounts at risk.
