## macOS (Sequoia 15 / Tahoe 26 / 27 beta): Screen Recording, Accessibility, Automation, FDA, Input Monitoring, sandbox/MAS, notarization, how Claude/ChatGPT request permissions

### Takeaway
A Relic-style screen-capture + UI-reading + input-posting app on macOS needs separate, user-granted TCC permissions for Screen Recording and Accessibility, and must ship as a signed .app bundle. Since Sequoia, Screen Recording triggers a recurring re-confirmation prompt (monthly as of the Sequoia betas). Apple DTS says the Accessibility APIs are not supported in sandboxed apps, so the full capability set is effectively incompatible with the Mac App Store. Plan for Developer ID + notarized direct distribution.

### Cited Findings
- During the Sequoia betas Apple changed the Screen Recording re-authorization prompt from weekly to monthly (beta 6), and Sequoia no longer re-prompts after every reboot — [9to5Mac](https://9to5mac.com/2024/08/14/macos-sequoia-screen-recording-prompt-monthly/); [MacRumors](https://www.macrumors.com/2024/08/15/macos-sequoia-screen-recording-app-permissions/) (search extract)
- macOS 15.1 reduced how often the prompt appears — [9to5Mac](https://9to5mac.com/2024/10/07/macos-sequoia-screen-recording-popups/) (title/search extract)
- An MDM key, `forceBypassScreenCaptureAlert`, lets managed devices suppress the monthly alert. Michael Tsai's roundup is titled "Sequoia Screen Recording Prompts and the Persistent Content Capture Entitlement", but the page itself could not be fetched to confirm the entitlement's terms — [Michael Tsai](https://mjtsai.com/blog/2024/08/08/sequoia-screen-recording-prompts-and-the-persistent-content-capture-entitlement/) (search extract)
- Workarounds such as editing replayd plist dates or changing the clock are fragile hacks — [Lapcat Software](https://lapcatsoftware.com/articles/2024/8/10.html); [TidBITS](https://tidbits.com/2024/09/23/how-to-avoid-sequoias-repetitive-screen-recording-permissions-prompts/) (search extract)
- An April 2026 third-party guide says the 30-day re-authorization still applies to third-party apps on Sequoia 15.x, and that an in-progress recording is not interrupted when the authorization expires — [Screenify](https://www.screenify.studio/blog/2026-04-10-screen-record-macos-sequoia) (secondary, search extract)
- Tahoe 26.1: developers report that unbundled command-line executables no longer appear in "Screen & System Audio Recording" settings (though they are reportedly still prompted and can capture once granted), and ScreenCaptureKit returns TCC decline error -3801 for unbundled tools. The suggested fix is a signed .app bundle with `NSScreenCaptureUsageDescription` — [Apple Dev Forums 807323](https://developer.apple.com/forums/thread/807323); [Apple Dev Forums 807898](https://developer.apple.com/forums/thread/807898); [trycua/cua #870](https://github.com/trycua/cua/issues/870) (search extract)
- `kCGWindowName` (window titles via CGWindowList) is only populated when the app holds Screen Recording permission — [Apple Dev Forums 756130](https://developer.apple.com/forums/thread/756130) (search extract)
- Apple DTS: "we do not support the Accessibility APIs in sandboxed apps". A different DTS answer says sandboxing does not prohibit the Accessibility permission itself and that some tasks, such as CGEventTap, can work sandboxed. A developer also reports that `AXUIElementSetAttributeValue` writes fail inside the App Sandbox even when Accessibility is granted, and that the sandbox suppresses the AX prompt — [Apple Dev Forums 756130](https://developer.apple.com/forums/thread/756130); [Apple Dev Forums 810677](https://developer.apple.com/forums/thread/810677); [Apple Dev Forums 24288](https://developer.apple.com/forums/thread/24288) (search extract; sources partly conflict)
- Mac App Store submissions are rejected without the sandbox (error 90296 "App sandbox not enabled") — [Apple Dev Forums 836644](https://developer.apple.com/forums/thread/836644) (search extract)
- Claude computer use on Mac (official Claude Code docs): it needs Accessibility (to click and type) plus Screen Recording (to see the screen). macOS may require a restart after Screen Recording is granted. Per-app access is approved per session ("Allow for this session"/"Deny") and does not carry over to the next session — [Claude Code docs: computer use](https://code.claude.com/docs/en/computer-use) (search extract)
- Third-party guides list Input Monitoring as optional for Claude computer use — [MindStudio](https://www.mindstudio.ai/blog/claude-code-computer-use-mac-setup-guide) (secondary, search extract)

### Inferences
- For Relic: capture via ScreenCaptureKit (Screen Recording TCC) plus UI text via AX (Accessibility TCC) leads to Developer ID signing, notarization and direct download, not the MAS. Expect a periodic Screen Recording re-confirm on Sequoia and later. MDM `forceBypassScreenCaptureAlert` is only an option for managed and enterprise fleets.
- Claude's pattern (OS-level TCC grants, then an in-app per-app, per-session allowlist) is a good consent model for Relic's agents.
- UNVERIFIED (training knowledge): the `com.apple.developer.persistent-content-capture` entitlement is a request-only managed entitlement meant for remote-desktop/VNC-type apps, and exempts them from the recurring prompt. A memory/recording app is unlikely to qualify. Confirm on Apple's entitlement docs.
- UNVERIFIED (training knowledge): Apple Events/Automation prompts once per target app (needs `NSAppleEventsUsageDescription`; sandboxed apps need the `com.apple.security.automation.apple-events` or scripting-targets entitlements). Full Disk Access cannot be requested programmatically, and the user must add the app manually. Input Monitoring governs CGEventTap/IOHID listen access. Notarization is required for Developer ID apps to pass Gatekeeper without warnings.

- Could not fetch the persistent-content-capture entitlement terms.

## Windows 11: UI Automation, Graphics Capture permissions, WDA_EXCLUDEFROMCAPTURE, Recall APIs, Copilot agent workspace, signing/SmartScreen

### Takeaway
Windows has no TCC-style prompt for desktop (Win32) screen capture or UIA. The main consent surfaces are the Graphics Capture border and borderless/programmatic consent APIs, and the new opt-in "agent workspace" for agentic features. Apps can opt their windows out of capture with `WDA_EXCLUDEFROMCAPTURE`, which Relic must respect, and which also hides those windows from Relic.

### Cited Findings
- `GraphicsCaptureAccessKind` has `Borderless` (0) and `Programmatic` (1). Both are requested via `GraphicsCaptureAccess.RequestAccessAsync`, which shows a user prompt. Borderless requires the `graphicsCaptureWithoutBorder` manifest capability. If the user declines, `IsBorderRequired=false` is ignored and the yellow border stays — [MS Learn: RequestAccessAsync](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscaptureaccess.requestaccessasync?view=winrt-20348); [MS Learn: IsBorderRequired](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession.isborderrequired); [MS Learn: screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) (search extract)
- `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` removes a window from capture entirely (Windows 10 2004+) and is the developer method for excluding a window from Recall. It can be toggled on demand — [Meziantou](https://www.meziantou.net/how-to-exclude-your-windows-app-from-screen-capture-and-recall.htm); [Electron commit](https://ayakael.net/mirrors/electron/commit/bf68405a2f2a1be6218076186118b16b74a687b5?files=docs) (secondary, search extract)
- Recall excludes InPrivate/incognito browsing and DRM content by default. Users can filter apps and websites in Settings — [Pureinfotech](https://pureinfotech.com/exclude-apps-websites-recall-windows-11/) (secondary, search extract)
- Agent workspace / Copilot Actions: opt-in. Agent accounts are provisioned only when the user enables the agent workspace. In preview, agents get a limited set of known folders (Documents, Downloads, Desktop, Pictures), and access beyond those needs user authorization. Users can monitor and take over, and sensitive steps may require approval. Agent connectors are MCP servers. Microsoft calls for signing of agent binaries and connectors so they can be revoked — [Microsoft Support: Experimental agentic features](https://support.microsoft.com/en-us/windows/ai/ai-features/experimental-agentic-features); [Windows blog: Securing AI agents on Windows (2025-10-16)](https://blogs.windows.com/windowsexperience/2025/10/16/securing-ai-agents-on-windows/); [Windows security book: agentic security](https://learn.microsoft.com/en-us/windows/security/book/operating-system-agentic-security) (search extract; pages not fetched)
- Third-party reporting: the toggle is off by default, requires an admin, and applies device-wide — [Petri](https://petri.com/windows-11-agentic-computing-workspaces/) (secondary)
- Claims of a "Windows Agent Runtime (Preview)" with per-agent capability grants at Build 2026 come only from a DEV Community post and are unverified — [DEV Community](https://dev.to/akaranjkar08/microsoft-build-2026-developer-preview-windows-agent-runtime-multi-model-copilot-and-the-agentic-5pi)

### Inferences
- Relic on Windows can capture screens with fewer OS prompts than on macOS. The bigger consent and trust work is product-level, plus SmartScreen reputation.
- Relic's agents could integrate as MCP agent connectors into the Windows agent framework. That would likely require code signing.
- UNVERIFIED (training knowledge): UIA requires no special permission for medium-integrity apps. Reading or driving elevated windows needs uiAccess=true, a signed binary and installation in a secure location. SmartScreen reputation builds per certificate and file. Since 2024, EV certificates no longer bypass SmartScreen instantly. Microsoft Artifact/Trusted Signing is the low-cost option.

### Gaps
- Could not confirm a public third-party "Recall API" (the User Activity API for Recall was announced in 2024 but not verified this session).
- The 2026 GA status of the agent workspace and Copilot Actions is unconfirmed.
- Code signing and SmartScreen policy were not verified this session.

## Android 15/16/17: MediaProjection consent, AccessibilityService Play policy, AppFunctions, Gemini actions, developer verification

### Takeaway
Google Play has banned AccessibilityService use for autonomous AI agents. The policy was announced 2025-10-30 and took effect 2026-01-28, with exemptions only for genuine disability tools (`isAccessibilityTool`) and deterministic scripted automation. That rules out an "AI agent drives the phone via a11y" design for Relic on Play. The sanctioned routes are AppFunctions (experimental; Android 16+; MCP-like on-device tools) and MediaProjection (per-session consent, with an app-only sharing option). Developer verification for sideloaded apps began enforcement on 2026-09-30 in four countries, with global rollout planned for 2027.

### Cited Findings
- Play AccessibilityService policy text: use of the Accessibility API that lets an app "autonomously initiate, plan, and execute actions or decisions" is prohibited. This "does not prohibit deterministic, rule-based automation, where behavior follows a static, human-defined script". "Verified accessibility tools, identified by the isAccessibilityTool="true" flag, are exempt from this prohibition and may use the Accessibility API for autonomous functionality, provided this functionality is for the app's core purpose of assisting people with disabilities." — [Play Console Help: Use of the AccessibilityService API](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en) (search extract; page blocked from direct fetch)
- Dates: announced 2025-10-30, effective 2026-01-28 — [Play Console Help: Policy deadlines](https://support.google.com/googleplay/android-developer/table/12921780?hl=en-GB); [Policy announcement: October 30, 2025](https://support.google.com/googleplay/android-developer/answer/16550159?hl=en) (search extract)
- Rationale from the announcement: such behavior "can change user settings without permission, circumvent Android's privacy controls, and leverage the user interface in a deceptive manner by executing actions without the user's knowledge or consent" — [Policy announcement: October 30, 2025](https://support.google.com/googleplay/android-developer/answer/16550159?hl=en) (search extract)
- Reports say Android 17 blocks apps not classified as accessibility tools from AccessibilityService when Advanced Protection Mode is on. Not confirmed from a Google primary source — [The Hacker News (2026-03)](https://thehackernews.com/2026/03/android-17-blocks-non-accessibility.html) (secondary)
- AppFunctions (fetched in full): "AppFunctions is in an experimental preview". It is "an Android platform API with an accompanying Jetpack library to simplify Android MCP integration" and lets apps "behave like on device MCP servers". "As of May 2026, AppFunctions integration with Gemini is in a private preview with trusted testers." Callers need the `EXECUTE_APP_FUNCTIONS` permission. It is available on Android 16 or higher, and functions are declared via the `@AppFunction` annotation — [Android Developers: AppFunctions](https://developer.android.com/ai/appfunctions)
- MediaProjection: since Android 14, users can share a single app instead of the whole display, which excludes system UI. A status bar chip lets the user stop sharing (the app gets `onStop()`). The `onCapturedContentResize` and `onCapturedContentVisibilityChanged` callbacks were added — [Android Developers: Media projection](https://developer.android.com/media/grow/media-projection); [Android 14 app screen sharing](https://developer.android.com/about/versions/14/features/app-screen-sharing) (search extract)
- Gemini agent on Android: a February 2026 beta (Pixel 10, Galaxy S26) automates multi-step tasks in food, grocery and rideshare apps, running the target app in a virtual window. "Gemini Intelligence" was announced at the Android Show: I/O Edition (May 2026), rolling out in waves from summer 2026. It is user-initiated, purchases require confirmation, and users can stop it at any time — [Business Today](https://www.businesstoday.in/amp/technology/news/story/geminis-agentic-era-is-here-it-can-now-automate-multi-step-tasks-on-android-apps-518098-2026-02-26); [Engadget](https://engadget.com/2170770/gemini-intelligence-brings-app-automation-to-android); [Android Authority](https://androidauthority.com/gemini-intelligence-3665302/) (secondary)
- Developer verification: Google blog (March 2026) says verification is "rolling out to all developers on Play Console and Android Developer Console". Enforcement began 2026-09-30 for installs from seven participating storefronts (Play, Galaxy Store, HONOR, OPPO, Xiaomi GetApps, vivo, Palm Store) on certified devices in Brazil, Indonesia, Singapore and Thailand, with global rollout in 2027. An "advanced flow" for installing unverified apps (Developer options toggle, warnings, one-time 24-hour wait) began rolling out in August 2026. ADB installs remain exempt — [Android Developers Blog (2026-03)](https://android-developers.googleblog.com/2026/03/android-developer-verification-rolling-out-to-all-developers.html); [9to5Google (2026-08-18)](https://9to5google.com/2026/08/18/google-gradually-rolling-out-androids-advanced-sideloading-ahead-of-developer-verification/); [Android Authority](https://www.androidauthority.com/google-android-advanced-flow-sideloading-rollout-begins-3700073/); [Android Authority timeline](https://www.androidauthority.com/android-sideloading-changes-timeline-3679204/) (search extract)
- Reports conflict on whether direct browser APK downloads fall under the current phase. One report says they are excluded for now — [Android Authority](https://www.androidauthority.com/android-developer-verification-rollout-sideloading-flow-3653395/) (search extract; conflicting)

### Inferences
- Relic on Android: an autonomous agent that acts through AccessibilityService is not shippable on Play, and Relic is not a disability tool. Even a sideloaded build would face developer verification (Relic's developer must register) and possibly Advanced Protection blocks.
- A read-only a11y "memory capture" is still a "sensitive" use needing prominent disclosure and Play review, and is risky. MediaProjection, with its per-session consent and visible chip, is the policy-safe capture path but is not continuous background capture.
- AppFunctions is the strategic fit for "Relic exposes memory to agents" on Android (Relic as an on-device MCP-style tool provider), but it is experimental and the Gemini integration is in private preview.

- Android 17 details were not confirmed from primary sources.

## iOS 26/27: App Intents, Shortcuts, ReplayKit, agent APIs, EU DMA

### Takeaway
iOS offers no general screen-capture-and-act path for third parties. The agent surface is App Intents, with onscreen awareness via NSUserActivity and View Annotation APIs, which Siri uses in the "27" releases. Relic on iOS should expose its memory as App Intents/entities rather than attempt capture.

### Cited Findings
- WWDC26: Siri in the 27 releases is "more capable, contextual, and personal", with App Intents as the foundation. Intents describe actions, parameters, and "when they're safe to run". The session covers App Schemas — [WWDC26 session 240](https://developer.apple.com/videos/play/wwdc2026/240/) (search extract)
- Onscreen awareness: adopting onscreen awareness APIs gives Siri context about which entities are on screen. Start with NSUserActivity and the View Annotation APIs — [WWDC26 session 343](https://developer.apple.com/videos/play/wwdc2026/343/) (search extract)
- Secondary claims (unverified against Apple): SiriKit was deprecated in favor of App Intents, and personal-context Siri requires iPhone 15 Pro or later — [Medium](https://medium.com/@adarsh.ranjan/ios-27-what-every-ios-developer-needs-to-know-e28ae44640fe); [Lushbinary](https://lushbinary.com/blog/wwdc-2026-announcements-ios-27-siri-developer-guide/) (secondary, unreliable)

### Inferences
- UNVERIFIED (training knowledge): ReplayKit broadcast upload extensions capture the whole screen only during a user-started broadcast (Control Center), and run under a tight memory limit of roughly 50 MB. They are unsuitable for always-on capture. EU DMA alternative marketplaces do not relax these sandbox/API limits.

## Agent interop protocols: MCP, A2A, AGENTS.md, llms.txt, Web Bot Auth

### Takeaway
MCP's latest spec revision is **2026-07-28**, not 2025-11-25. It is a major breaking revision: stateless (no initialize handshake, no sessions), with the multi round-trip request (MRTR) pattern replacing server-initiated elicitation and sampling. Authorization remains OAuth 2.1-based, using Protected Resource Metadata and Client ID Metadata Documents. The MCP Registry is still in preview. A2A reached v1.0 (2026-03-12; v1.0.1 on 2026-05-26) under the Linux Foundation. MCP and AGENTS.md now sit under the Linux Foundation's Agentic AI Foundation (AAIF, launched 2025-12-09). Web Bot Auth is now an IETF WG draft.

### Cited Findings
- MCP spec versions in the repo: 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28 and draft. docs.json labels "Version 2026-07-28 (latest)" — [MCP spec repo](https://github.com/modelcontextprotocol/modelcontextprotocol) (local clone, HEAD 2026-10-14)
- 2026-07-28 major changes (verbatim from the changelog): "Remove protocol-level sessions and the `Mcp-Session-Id` header" (SEP-2567); "Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake", with protocol version and capabilities carried in `_meta` on every request (SEP-2575); a new mandatory `server/discover` RPC; `subscriptions/listen` replaces the GET endpoint and resources/subscribe; `ping` and `logging/setLevel` are removed; tasks move to an official extension `io.modelcontextprotocol/tasks` (SEP-2663); "Multi Round-Trip Requests (MRTR) pattern introduced which replaces the previous approach of sending server-initiated requests, such as `roots/list`, `sampling/createMessage`, or `elicitation/create`", where servers return `InputRequiredResult` (SEP-2322); SSE resumability is removed — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) (local clone)
- 2026-07-28 minor changes: `extensions` capability field; OpenTelemetry `_meta` trace propagation; `Mcp-Method`/`Mcp-Name` headers; `ttlMs`/`cacheScope` cacheable results; RFC 9207 `iss` validation (SEP-2468); DCR `application_type` (SEP-837); credentials bound to the issuing authorization server (SEP-2352) — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) (local clone)
- 2025-11-25 changes: OpenID Connect Discovery; icons; incremental scope consent via `WWW-Authenticate`; URL-mode elicitation (SEP-1036); tool calling in sampling; Client ID Metadata Documents (SEP-991); experimental tasks (SEP-1686) — [MCP 2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog) (local clone)
- Authorization (2026-07-28): based on OAuth 2.1 (draft-ietf-oauth-v2-1-13). The protected MCP server acts as an OAuth 2.1 resource server and MUST implement RFC 9728 Protected Resource Metadata. Clients and authorization servers SHOULD support Client ID Metadata Documents — [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) (local clone)
- Elicitation (2026-07-28) has form mode and URL mode. "Servers MUST NOT use form mode elicitation to request sensitive information such as passwords, API keys, access tokens, or payment credentials", and must use URL mode for those — [MCP elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation) (local clone)
- Resources and prompts remain server features in 2026-07-28 (`server/resources.mdx`, `server/prompts.mdx`) — [MCP spec repo](https://github.com/modelcontextprotocol/modelcontextprotocol) (local clone)
- MCP Registry: "The MCP Registry is currently in preview. Breaking changes or data resets may occur before general availability." — [MCP registry docs](https://modelcontextprotocol.io/registry/about) (local clone)
- A2A: "an open source project under the Linux Foundation, contributed by Google", Apache 2.0. Releases: v0.3.0 (2025-07-30), v1.0.0 (2026-03-12), v1.0.1 (2026-05-26). v1.0 makes a2a.proto normative, adds signed Agent Cards (JWS + RFC 8785 JCS), mTLS, OAuth Device Code flow, `pkce_required`, multi-tenancy, renames operations (`message/send` becomes `SendMessage`) and uses SCREAMING_SNAKE_CASE enums (breaking) — [A2A repo README/CHANGELOG/whats-new-v1](https://github.com/a2aproject/A2A) (local clone, HEAD 2026-10-15)
- AAIF launched 2025-12-09 as a Linux Foundation project, with MCP (from Anthropic), AGENTS.md (from OpenAI) and goose (from Block) as founding projects — [SD Times](https://sdtimes.com/ai/linux-foundation-forms-agentic-ai-foundation-to-be-new-home-for-mcp-goose-and-agents-md/); [InfoQ](https://infoq.com/news/2025/12/agentic-ai-foundation/); [ITPro](https://itpro.com/software/open-source/anthropic-says-mcp-will-stay-open-neutral-and-community-driven-after-donating-project-to-linux-foundation) (search extract; one source conflicts on who donated AGENTS.md)
- Web Bot Auth: `draft-ietf-webbotauth-httpsig-protocol-00` (dated September 2026, a WG document) defines HTTP Message Signatures for bots, a `Signature-Agent` header, a JWKS key directory and a well-known URI. Companion drafts are the architecture draft (meunier-05, March 2026) and a registry draft with a "Signature Agent Card" — [IETF Datatracker](https://datatracker.ietf.org/doc/html/draft-ietf-webbotauth-httpsig-protocol); [architecture draft](https://datatracker.ietf.org/doc/html/draft-meunier-web-bot-auth-architecture-05) (search extract)
- The A2A docs site itself publishes `llms.txt` and `llms-reference.txt` (docs/llms.txt in the repo), showing llms.txt adoption by protocol projects — [A2A repo](https://github.com/a2aproject/A2A) (local clone)

### Inferences
- Relic's memory-to-agents interface should target MCP 2026-07-28 (stateless, MRTR) while keeping backward compatibility with 2025-06-18 and 2025-11-25 clients, since many hosts will lag. Use URL-mode elicitation for any consent or credential step. For a local stdio server, OAuth is not required; a remote or sync relay needs OAuth 2.1 + PRM + CIMD.
- A2A v1.0 signed Agent Cards and Web Bot Auth signatures are both usable for "signed, consent-scoped agent identity" if Relic exposes agents across devices or to the web.

### Gaps
- No primary source fetched for the llms.txt spec status (llmstxt.org) or the AGENTS.md site.
- Whether Web Bot Auth is deployed in production by Anthropic or OpenAI is unverified (sources conflict).
