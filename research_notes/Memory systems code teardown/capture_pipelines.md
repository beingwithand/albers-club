## 1. Capture triggers, OS APIs, dedup: how each system decides what to capture

### Takeaway
The pipelines have moved from fixed-interval screenshots plus a pixel diff (OpenRecall, Windrecorder, Dayflow) to event-driven, accessibility-first capture (Screenpipe). Screenpipe captures on UI events (app switch, focus, click, typing pause, scroll stop, clipboard). It reads the accessibility tree first, runs OCR only on text-region crops whose pixel signature changed, and falls back to an idle snapshot every 30 s. ActivityWatch captures no pixels at all: it polls metadata every 1 s and merges the polls into heartbeat events.

### Cited Findings
**Screenpipe (Rust, most advanced)**
- The event-driven loop "replaces the polling-based `continuous_capture`… Captures happen only on meaningful user events: app switch, window focus, click, typing pause, scroll stop, clipboard, and periodic idle fallback." Trigger enum: `app_switch, window_focus, click, typing_pause, scroll_stop, key_press, clipboard, visual_change, idle, manual`. The trigger name is stored in `frames.capture_trigger`. — [SP crates/screenpipe-engine/src/event_driven_capture.rs L5-9, L522-536](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-engine/src/event_driven_capture.rs#L5-L9)
- Default config: `min_capture_interval_ms: 200` (debounce), `idle_capture_interval_ms: 30_000`, `jpeg_quality: 80`, `visual_check_interval_ms: 3_000`, `visual_change_threshold: 0.05` ("~5% difference triggers capture"). Battery-saver PowerProfiles can relax the idle interval "up to 300s". Soft checkpoints (KeyPress/TypingPause) have a 1,500 ms floor (`CHECKPOINT_MIN_INTERVAL_MS`). During meetings a forced capture fires every 5 s (`MEETING_IDLE_CAPTURE_INTERVAL_MS`). — [SP event_driven_capture.rs L557-605, L622, L633](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-engine/src/event_driven_capture.rs#L557-L633)
- Visual-change detector optimizations (documented in the code): (1) a hash of the downscaled frame gives an early exit for identical frames, (2) a proportional 1/4 downscale ("Factor 6 (320px) caused hash collisions on dense text"), (3) a single metric, a grayscale histogram with Hellinger distance (`image_compare::gray_similarity_histogram(Metric::Hellinger…)`), instead of histogram+SSIM, which saves "40-50%". The cost is ~10 ms per cycle. — [SP crates/screenpipe-screen/src/frame_comparison.rs L8-20, L77-111, L378-380](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-screen/src/frame_comparison.rs#L8-L20)
- "Paired capture": the screenshot and the accessibility-tree walk happen as one atomic operation. The JPEG snapshot is written to disk and a frame row is inserted with the accessibility text and the snapshot path. — [SP crates/screenpipe-capture/src/paired_capture.rs L5-12](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-capture/src/paired_capture.rs#L5-L12)
- OCR gate pipeline: "screenshot -> crop to the focused app window -> detect text regions -> crop to the padded union of the detected text -> pixel-compare that crop to the last indexed one -> different? run OCR on that same crop". Detection costs ~10-20 ms and hashing ~1-3 ms; OCR ("hundreds of ms") runs only when the crop changed. The gate keeps one signature per app. Earlier heuristics (geometry fingerprints, stability waits, region-scoped hashes) "each produced wrong skips". A signature is committed only after the DB write is confirmed durable (`ocr_indexed`), so failed OCRs are retried. Skipped captures reuse the last OCR text, which gives no-a11y apps such as terminals text at zero OCR cost. — [SP crates/screenpipe-capture/src/ocr_gate.rs L5-75](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-capture/src/ocr_gate.rs#L5-L75)
- Accessibility-text dedup: a 64-bit SimHash per (app, window) with Hamming threshold `SIMHASH_THRESHOLD = 10` ("scrolling changes ~10-20% of content… roughly 5-10 bit differences"). A cache of 100 entries with a 60 s TTL. — [SP crates/screenpipe-a11y/src/tree/cache.rs L14-50](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-a11y/src/tree/cache.rs#L14-L50)
- Tree-walk budget defaults: `max_depth: 35, max_nodes: 5000, walk_timeout: 250ms`, with an adaptive per-app override. — [SP crates/screenpipe-a11y/src/tree/mod.rs L566-568](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-a11y/src/tree/mod.rs#L566-L568)
- OS APIs: on macOS, `sck-rs` (ScreenCaptureKit, 12.3+) with `xcap` as the fallback. On Windows, `xcap` with the `wgc` feature (Windows Graphics Capture) plus a separate `wgc_capture.rs`. Accessibility trees come from macOS AX, Windows UI Automation (`windows_uia.rs` uses a CacheRequest that includes `UIA_IsPasswordPropertyId`) and Linux AT-SPI (`check_atspi_available`). — [SP crates/screenpipe-screen/Cargo.toml L84-101](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-screen/Cargo.toml#L84-L101); [SP crates/screenpipe-a11y/src/platform/windows_uia.rs L596](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-a11y/src/platform/windows_uia.rs#L596)

### Inferences
- The best-in-class trigger design for Relic is Screenpipe's stack: OS events plus an idle fallback, a cheap 1/4-scale histogram check on a 3 s interval, a11y text first, and OCR only on changed text-region crops. Each layer removes most of the work before the expensive step runs. Fixed-interval full-frame OCR (OpenRecall: DocTR on every changed frame every 3 s) is the costly anti-pattern.
- "Commit the dedup baseline only after a durable write" appears independently in Screenpipe (`ocr_indexed`) and Windrecorder ("only accepted OCR advances the baseline"). It is a cheap correctness rule worth copying.
- The ActivityWatch heartbeat model is the right primitive for the metadata layer (app, window, URL, AFK): 1 s polls collapse into a few rows per hour.

### Gaps
- Screenpipe's Linux pixel-capture backend (xcap vs. PipeWire portal) and its Wayland handling were not traced.
- How Screenpipe chooses the default OCR engine per platform at runtime was not confirmed. The `OcrEngine` enum's `#[default]` is `Tesseract` ([SP crates/screenpipe-screen/src/utils.rs L14-17](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-screen/src/utils.rs#L14-L17)), but the platform config may override it.

## 2. OCR engines, audio pipeline, video encoding, storage schema and indexing

### Takeaway
Native OS OCR wins on cost: Apple Vision on macOS and Windows.Media.Ocr on Windows, with Tesseract or ONNX models as cross-platform fallbacks. Screenpipe's audio stack is Silero VAD, 30 s chunks and Whisper large-v3-turbo by default (Parakeet optional). Video is moving from continuous x265 recording to JPEG snapshots that are later compacted with a hardware or libx264 encoder and a 25-frame GOP. Screenpipe's schema relies on FTS5 in external-content mode and has dropped its OCR-embedding table. Timelinize and Windrecorder add vector search: SigLIP2 with sqlite-vec, and uform3 with faiss.

### Cited Findings

- Screenpipe supports Apple Vision (`RecognizeTextRequest` with `set_uses_lang_correction(false)` and explicit language list), Windows `Windows.Media.Ocr` (`TryCreateFromUserProfileLanguages`, engine cached per language set), Tesseract, a cloud "Unstructured" engine and Custom. — [SP crates/screenpipe-screen/src/apple.rs L170-181](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-screen/src/apple.rs#L170-L181); [SP crates/screenpipe-screen/src/core.rs L554-569](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-screen/src/core.rs#L554-L569); [SP crates/screenpipe-screen/src/microsoft.rs L271-294](https://github.com/mediar-ai/screenpipe/blob/3722ba4433a964c91313182b071ab83173cc3ec4/crates/screenpipe-screen/src/microsoft.rs#L271-L294)

- Schema to copy for Relic: three layers. (1) An ActivityWatch-style `buckets/events(start, end, data JSON)` table for low-cost metadata intervals. - Store snapshots as JPEG files and compact them into H.264/HEVC chunks later with a short GOP (~25). This beats continuous video recording on both CPU and seek latency, per Screenpipe's own benchmarks.

## 3. Privacy filters, LLM summarization (Dayflow), Timelinize data model and importer interface

### Takeaway
The privacy controls are layered. Screenpipe has the most: per-app and per-window exclusion, incognito detection by title in more than 20 locales (plus AppleScript), skipping of secure text fields, regex PII redaction and ONNX image redaction. ActivityWatch has drop/redact regex rules at the datastore level, and Dayflow and Windrecorder seed lists of password-manager apps to block. Dayflow's summarizer batches 15 minutes of screenshots into one strongly constrained JSON timeline-card prompt with a 10-60 min card rule, and skips the LLM for idle batches. Timelinize's AGPL schema of items, entities, attributes and relationships, with timestamp/timespan/timeframe/time_uncertainty, is the strongest model for a general lifelog.

### Inferences
- Relic should model captured screen and audio activity as Timelinize-style `items`: classification "screen_session" or "transcript", `timestamp` + `timespan`, an `attribute_id` owner, and `relationships` to people and documents. Adopt the timespan vs. timeframe vs. time_uncertainty distinction as well. Because Timelinize is AGPL, re-implement the design rather than copy the code.
- Dayflow's prompt rules (10-60 min cards, merge bias, distractions sub-array, "grounded in screenshot" constraint, idle short-circuit) are the most reusable LLM-summarization design. Dayflow is MIT, so the prompt text is reusable with attribution.

### Gaps
- Dayflow's full Gemini video-transcription prompt (the two-step path: video → observations → cards) was not read in full. Only the one-step Claude/Codex prompt and the Ollama path were examined.
- Screenpipe's ONNX/RF-DETR image-redaction model specifics (which classes, what latency) were not traced.

### Inferences
- A "best of" capture stack for Relic:
  - Capture: native capture APIs (ScreenCaptureKit / Windows Graphics Capture / PipeWire) triggered by events, with a 30 s idle fallback.
  - Metadata: an ActivityWatch-style heartbeat bucket for app, window, URL and AFK.
  - Text: a11y text first, with Apple Vision or Windows.Media.Ocr on changed text crops as the fallback.
  - Storage: JPEG snapshots compacted to H.264/HEVC with GOP 25; SQLite external-content FTS5 plus sqlite-vec only on summaries.
  - Summaries: Dayflow-style 15-minute batches with a 10-60 min card prompt and idle short-circuit.
  - Lifelog model: Timelinize-style items, entities and relationships for the long-term record.
  - Privacy: Screenpipe-style privacy layering, re-implemented clean-room.
- MPL-2.0 permits reusing the ActivityWatch heartbeat/merge code in a closed app, provided modified MPL files stay open. MIT Dayflow code and prompts can be adapted freely with attribution.

### Gaps
- No runtime CPU, RAM or disk measurements were taken (the code was not executed). The performance numbers above are the projects' own comments in code and were not independently verified.
- OpenRecall's upstream activity is low (last commit 2025-09-24), so its maintenance status may matter. Whether newer forks exist was not checked.
