## 1. Exact context-window layout (what goes in which section)

### Takeaway
Letta builds a single **system message** from the base instructions with `{CORE_MEMORY}` replaced by: `<memory_blocks>` (each block holds an XML `<label>` with `<description>`, `<metadata>` (chars_current/chars_limit) and `<value>`), then any open-file blocks, then a `<memory_metadata>` stats footer. After the system message come an optional **summary message** (`system_alert` JSON, role `summary` or `user`) and then the recent message FIFO. Recall and archival memory stay out of context. The context only gets **counts** of what they hold, plus the archival tag list. MemOS has no single fixed prompt layout. It retrieves graph memories (WorkingMemory/LongTermMemory/UserMemory, ...) and injects them per query.

### Inferences
- For Relic, Letta's layout is simple to copy: one system string = static instructions + XML blocks with `chars_current/limit` + a stats footer, followed by an optional rolling summary message and then the raw recent turns. The stats footer tells the model that out-of-context stores exist, which encourages it to search them.
- Relic should enforce block limits in code, as OLD did and LA no longer does. Otherwise blocks grow without bound and silently eat the context budget.
- MemOS's "MemCube with parametric/activation memory" mostly exists on paper. In code, only the textual graph memory is mature. LoRA is a placeholder and KV-cache memory requires HF transformers with local weights.

## 2. When and how summarization or eviction triggers

### Takeaway
**Original MemGPT:** warn at 75% of context ("save important info now"), then truncate to about 75% while keeping the last 3 messages, with a recursive summary. **Letta archive (current server):** no pre-warning by default. Compaction runs when the token estimate exceeds `0.9 × context_window` (post-step), or reactively on a provider `ContextWindowExceededError` (up to 3 retries). The default mode is `sliding_window`: evict at least 30% of messages, growing the cut in 10% steps until the remainder is under 70% of the window. The cut must land on an assistant message. A cheaper summarizer model produces a ≤300-word structured summary, clipped at 50,000 chars, which is placed right after the system message. Evicted messages remain searchable in recall.

### Cited Findings
- **Trigger threshold.** `SUMMARIZATION_TRIGGER_MULTIPLIER = 0.9  # using instead of 1.0 to avoid "too many tokens in prompt" fallbacks`. `get_compaction_trigger_threshold` returns `int(llm_config.context_window * SUMMARIZATION_TRIGGER_MULTIPLIER)` for **all** models. Its docstring says "All other models trigger at 100%", which **contradicts** the code. — [LA constants.py L81-L83](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/constants.py#L81-L83); [LA letta/services/summarizer/thresholds.py](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/services/summarizer/thresholds.py)
- **Agent loop call sites.** The threshold is computed at [LA letta/agents/letta_agent_v3.py L938](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/agents/letta_agent_v3.py#L938). The reactive path runs `if isinstance(e, ContextWindowExceededError) and llm_request_attempt < summarizer_settings.max_summarizer_retries` (L1218-L1241). The proactive path is `trigger="post_step_context_check"` (L1450-L1470). If compaction cannot fit the context, the run stops with `context_window_overflow_in_system_prompt`.
- **Settings.** `mode = PARTIAL_EVICT_MESSAGE_BUFFER`, `message_buffer_limit = 60`, `message_buffer_min = 15`, `max_summarization_retries = 3`, `partial_evict_summarizer_percentage = 0.30` ("eviction based on percentage of message count, not token count"), `memory_warning_threshold = 0.75`, `send_memory_warning_message = False`, `desired_memory_token_pressure = 0.3`, `keep_last_n_messages = 0`. — [LA letta/settings.py L74-L111](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/settings.py#L74-L111)
- **CompactionSettings.** `mode` is one of `"all" | "sliding_window" | "self_compact_all" | "self_compact_sliding_window"` (default `sliding_window`), `clip_chars = 50000`, and the summarizer `model` defaults per provider: `anthropic/claude-haiku-4-5`, `openai/gpt-5-mini`, `google_ai/gemini-2.5-flash`. The "self_*" modes use the agent's own model and context, which makes cache reuse possible. — [LA letta/services/summarizer/summarizer_config.py](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/services/summarizer/summarizer_config.py)
- **Sliding-window algorithm**, from the docstring: "1. Start at a message index cutoff (1-N%) 2. Count tokens with system prompt, prior summary... and messages past cutoff point 3. Is count(post_sum_messages) <= N% of agent's context window? 3a. Yes -> create new summary with [prior summary, cutoff:]... 3b. No -> increment cutoff by 10%, and repeat". The code computes `goal_tokens = (1 - sliding_window_percentage) * context_window` and keeps incrementing `eviction_percentage += 0.10`. A cutoff must be an assistant message (or an approval message with tool calls) so that tool-call/return pairs are not split. A pending approval request is never evicted. On failure it raises, and the caller falls back to `summarize_all`. — [LA letta/services/summarizer/summarizer_sliding_window.py L99-L232](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/services/summarizer/summarizer_sliding_window.py#L99-L232); fallback chain in [LA letta/services/summarizer/compact.py L135-L470](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/services/summarizer/compact.py#L135-L470)

Write a detailed summary that captures what happened in these messages to appear BEFORE the remaining recent messages in context..." Sections: High level goals / What happened / Important details ("Preserve identifiers verbatim") / Errors and fixes / Lookup hints ("note the topic and key terms that could be used to find it in message history later"). Limits: `SLIDING_WORD_LIMIT = 300` and `ALL_WORD_LIMIT = 500`, with "Write in first person as a factual record". — [LA letta/prompts/summarizer_prompt.py L1-L97](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/prompts/summarizer_prompt.py)

### Inferences
- Letta's design has moved from a "warn then let the agent save" approach to "summarize automatically with a cheap model". In practice they apparently did not rely on the agent saving under pressure: the warning is off by default, and the background reflection or sleep-time agent now does the saving.
- A Relic recipe: trigger at about 0.9 of the local model's context, keep about 70%, cut only at assistant boundaries, write a ≤300-word structured summary with "lookup hints", and keep every raw message in SQLite FTS so `conversation_search` can recover what was evicted.

## 3. How the agent decides to write memory (self-editing tools)

### Takeaway
In Letta the **LLM decides**, through tool calls guided only by prompt text: append/replace/insert/rethink on blocks, plus archival insert. Writes are string operations validated in code (exact match, unique occurrence, no line-number prefixes). MemOS does **not** let the agent decide. An extraction LLM (mem_reader) runs on every ingested chat window and emits JSON memories. Merging uses embedding similarity plus an LLM merge prompt, and the graph reorganizer and Dream run later.

### Cited Findings

### Inferences
- These are two different write policies. Agentic writes (Letta) are flexible but depend on the model's tool-use reliability and judgment, and they cost latency in the foreground. - For Relic: keep a minimal foreground tool set (search plus at most a precise `memory_replace`/`memory_insert`) and move rethink and consolidation to the background. This is the arrangement Letta itself uses when sleep-time is enabled.

## 4. How background consolidation runs (sleep-time agents, reflection, MemOS reorganizer and Dream)

### Takeaway
**Letta sleep-time:** a second agent shares the main agent's blocks by ID and runs as a fire-and-forget asyncio task every N=5 turns (default). It receives a transcript of the messages since the last processed message and edits blocks with replace/insert/rethink/finish_edits. **letta-code reflection:** a background subagent with only Bash and Edit tools, triggered by compaction (or every 25 steps). It edits a git repo of markdown memory and commits. **MemOS:** a queue-driven scheduler (labels add/mem_read/mem_organize/mem_dream/...). A graph reorganizer thread does KMeans clustering, LLM cluster summaries into parent nodes and relation/inference detection. The opt-in "Dream" plugin fires after 100 pending memories and produces insights and a diary.

### Inferences
- The simplest consolidation loop worth replicating is Letta v4: every N turns, enqueue a background job with (transcript since cursor, current blocks), let a model make precise edits or a `rethink`, then advance the cursor. Its weakness is that the job is fire-and-forget (`safe_create_task`) with no persistent queue. If the process dies, the work is lost, but the cursor has already advanced, because `get_last_processed_message_id_and_update_async` runs **before** the task. A local app should persist the job and advance the cursor only when the job completes.
- letta-code's git-backed markdown memory gives versioning, diffs and rollback for free. It is the most robust option on-device: an atomic commit per reflection, and the user can audit it.
- MemOS's reorganizer is heavyweight (KMeans, LLM sub-clustering, relation inference, a graph DB). The Dream "insight" generation is speculative and still beta.

## 5. What can run on small local models

### Takeaway
Most mechanisms are plain code: block rendering, token counting, sliding-window cut selection, FTS and vector search, turn counters, KMeans. The LLM-dependent parts are (a) reliable tool calls for self-editing, (b) the ~300-word structured summary, (c) JSON extraction and merge decisions, and (d) consolidation rewrites. Letta itself delegates summarization to small "mini/haiku/flash" models. MemOS's local plugin runs entirely on SQLite with FTS5, local MiniLM embeddings and an ONNX runtime.

### Inferences
- **Small local model (3-8B) can handle:** the sliding-window summary (a single prompt with fixed sections and a word cap); MemOS-style JSON extraction with key/value/tags; merge yes/no decisions; and precise `memory_insert` appends. Foreground agentic self-editing with exact-match `old_string` and multi-step rethink is the riskiest piece on small models. Relic should route edits through a background job that can retry and validate, as Letta's sleep-time agent and letta-code's reflection do, rather than through the chat model mid-turn.
- **Pure code, no LLM:** a FTS5 plus 384-dim MiniLM hybrid search (as memos-local-plugin does); turn-count and compaction-event triggers; KMeans grouping before any LLM consolidation.
- A KV-cache "activation memory" (MemOS) is a real on-device opportunity: precompute the KV cache for the static system prompt and core blocks, and invalidate it on block edits. This matches why Letta's "self_compact" mode avoids refreshing the system prompt ("so we can leverage cache").

### Gaps
- No benchmark numbers were found for Letta or MemOS memory quality on small local models specifically.

## 6. Weaknesses and pitfalls (code vs. paper)

### Takeaway
The main risks are unenforced block limits, a sleep-time cursor that advances before the work completes, dead periodic-schedule code in MemOS, docstring/code mismatches in thresholds, parametric memory that exists in the paper but not the code, beta Dream state that is in-memory only, and a heavy infrastructure footprint for MemOS server mode.

### Cited Findings
- **Letta block `limit`** is displayed but not enforced in the archive's `update_block_value`. OLD enforced it. — [LA schemas/memory.py L771-L780](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/schemas/memory.py#L771-L780); [OLD memgpt/memory.py L47](https://github.com/letta-ai/letta/blob/a1140032929ebbc33772d8fb67ea86d259d540e4/memgpt/memory.py#L47)
- **Threshold docstring mismatch:** "All other models trigger at 100%" vs `return int(context_window * 0.9)`. — [LA thresholds.py](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/services/summarizer/thresholds.py)
- **Sleep-time cursor ordering:** `last_processed_message_id` is updated before `safe_create_task`, and failures are only `print`-ed and re-raised. — [LA sleeptime_multi_agent_v4.py L152-L166](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/groups/sleeptime_multi_agent_v4.py#L152-L166)
- **Sliding-window eviction granularity:** eviction is by **message-count percentage**, not tokens ("eviction based on percentage of message count, not token count"). It can fail ("No assistant message found..."), and then falls back to summarizing everything. — [LA settings.py L84-L86](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/settings.py#L84-L86); [LA summarizer_sliding_window.py L193-L197](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/services/summarizer/summarizer_sliding_window.py#L193-L197)
- **Letta repo churn:** the Python server is now archived ("retired Letta V1 API server"), and archival insert/search tools are marked deprecated. — [LA main README](https://github.com/letta-ai/letta/blob/5bcdd177d70fa2b31a754cfcd801e77b2e1ab16a/README.md); [LA constants.py L108](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/constants.py#L108)
- **MemOS:** LoRA parametric memory is a "placeholder"; Dream signals "do not survive process restarts"; the reorganizer's `schedule.every(100)` jobs are never run (no `run_pending`); the extraction prompt over-extracts by design ("Prioritize completeness and fidelity over conciseness"); and server mode needs Neo4j and Qdrant. — links in §1, §3 and §4 above.
- **Benchmarks are self-reported:** MemOS LOCOMO results use gpt-4o-mini as the judge. — [arXiv 2507.03724](https://arxiv.org/pdf/2507.03724)

### Inferences
- Relic should: enforce limits and return the error text to the model, as OLD did; persist background jobs with idempotent cursors; version memory (git or a SQLite history table, like letta-code commits or MemOS `ArchivedTextualMemory`); keep a status lifecycle (`activated/resolving/archived/deleted`) instead of hard deletes; and normalize relative dates to absolute ones at write time. Both systems' prompts insist on that last point.

- I did not read MemOS's `mem_feedback` correction loop or the memos-local-plugin L2/L3 induction algorithms in detail. Their docs are under `apps/memos-local-plugin/docs/`.
